# گزارش اجرای اتصال مشتری Native به Stage

۵ نوامبر ۲۰۲۶ به وقت تهران — در حال آزمون؛ تأیید نسخه نهایی نیست.

## منابع بررسی‌شده

- مخزن `mrstud3nt/namyran-customer-android`، شاخه `codex/stage-core-integration` و PR شماره ۱؛ بدون ادغام.
- نسخه خوانده‌شده فایل اصلی Core روی Stage: `2.0.0-alpha.5.81`؛ ثابت DB برابر `2.0.0-alpha.5.5` است و اجرای Migration مستقلاً تأیید نشده است.
- ZIP ارسالی کاربر با SHA-256 برابر `c35b17fd4778eb49286e7dc9a3b93463bb12a656be6dc257354c6e57d28f9a1b` استخراج شد. فایل‌های frontend.js و public-session.js آن با فایل‌های زنده Stage یکسان‌اند. این نتیجه اثبات یکسان بودن تمام فایل‌های نصب‌شده نیست.
- سورس REST، Guard، Policy Registry، Shortcode، Utils، Catalog، Geo Data، Locations و جریان JavaScript فرم بررسی شدند. ZIP کامل Core در مخزن عمومی Android منتشر نمی‌شود.

## قرارداد واقعی Core

- خدمات، گروه‌ها، دستگاه‌ها، زیرنوع‌ها، خدمات هر دستگاه، نسخه ردیف‌ها، برندها و تنظیمات نصب از پیکربندی جاری Core می‌آیند.
- مدل و شرح مشکل ورودی آزادند؛ فهرست مدل/مشکل اختراع نشده است.
- شهرها فقط از active_service_catalog خوانده می‌شوند؛ هیچ شهر پیش‌فرضی فعال نمی‌شود.
- زمان مراجعه پیشنهاد مشتری است. Core فعلی زمان گذشته/فاصله اعزام را کنترل می‌کند و در این قرارداد شمارنده ظرفیت قابل رزرو ارائه نمی‌دهد. اپ آن را رزرو قطعی نمی‌نامد.
- API ثبت فعلی فیلد مستقل city را ذخیره نمی‌کند. اپ نام شهر و محله انتخاب‌شده را در نشانی ارسال می‌کند؛ ادعای ذخیره ستون city ندارد.
- نشست عمومی با bootstrap موجود و Origin/Referer همان Stage دریافت می‌شود؛ OTP، ثبت، فهرست حساب و پیگیری از API موجود Core استفاده می‌کنند.

## پیاده‌سازی این شاخه

- رابط Kotlin/Compose با حالت روشن/تاریک، خانه، ورود، فهرست و جزئیات درخواست و فرم چنددستگاهی جایگزین پیش‌نمایش آفلاین شد.
- افزونه مستقل Stage Bridge، فقط دو مسیر GET برای config و schedule دارد. کاتالوگ را از خروجی پیکربندی خود فرم Core، شهرها را از Geo Data و بازه‌ها را از تابع زمان‌بندی Core می‌گیرد. مسیرهای ثبت و احراز هویت Core تغییر نمی‌کنند.
- ارتباط به HTTPS و دامنه دقیق Stage محدود است؛ Redirect دنبال نمی‌شود؛ credential مدیریتی در APK وجود ندارد.
- نشست و پیش‌نویس با Android Keystore رمزگذاری می‌شوند. در ثبت مبهم، payload و submission_token حفظ و به حساب اولیه محدود می‌شوند. ثبت موفق فقط با شناسه و کد پیگیری معتبر پذیرفته می‌شود و سپس همان کد در my-requests بازخوانی می‌شود؛ شکست بازخوانی جدا نمایش داده می‌شود.
- داده نمونه یا کد OTP ثابت در اپ نیست. پاسخ dev_mode در ارسال OTP به‌عنوان تحویل واقعی پذیرفته نمی‌شود.

بررسی GET واقعی و فقط‌خواندنی در ۴ نوامبر ۲۰۲۶: config با HTTP 200 و no-store/private، شامل ۴ خدمت، ۶ گروه، ۲۹ دستگاه فعال، ۱۲ برند عمومی، ۷ برند نصب و یک شهر فعال (شیراز) با ۲۰۱ ناحیه بود. داده خدمات/گروه‌ها/برندها/تنظیمات تلویزیون و مراجعه با فرم زنده Core تطبیق داشت. زمان پیشنهادی فردا ۴ بازه برگرداند؛ تاریخ گذشته و نامعتبر با HTTP 400 رد شدند. جزئیات در [stage-readonly.json](evidence/stage-readonly.json) ثبت شده است. این شمارش snapshot است؛ داده اپ از Core خوانده می‌شود.

## آزمون زنده OTP و ثبت واقعی پس از دریافت اجازه

کاربر شماره آزمایشی، کد دریافتی و سپس نام مشتری و اجازه استفاده از نشانی و موقعیت ساختگی را ارائه کرد. ارسال OTP با HTTP 200 و dev_mode=false، تأیید کد با HTTP 200 و دریافت نشست، و بازخوانی حساب با HTTP 200 موفق شدند. پس از ثبت، حساب دقیقاً همان کد پیگیری را برگرداند و مسیر track نیز success=true داشت.

درخواست واقعی Stage با شناسه ۱ ایجاد شد: دستگاه تلویزیون از گروه صوتی و تصویری با catalog_id=6 و row_version=1؛ خدمت تعمیر تخصصی و برند پیش‌فرض آزمایشی LG از داده زنده Core انتخاب شدند. نام ارسالی کاربر به‌کار رفت؛ نشانی و مختصات طبق اجازه او ساختگی و صریحاً با «تست؛ بدون اعزام» توصیف شدند. این متن یک برچسب است و مکانیزم Core برای خاموش کردن اعزام یا اعلان را تغییر نمی‌دهد. تاریخ پیشنهادی 2026-11-06 و بازه ۱۰ تا ۱۲ از schedule زنده انتخاب شد؛ رزرو ظرفیت تکنسین ادعا نمی‌شود.

این آزمون از API واقعی عمومی Core با همان قرارداد payload اپ انجام شد؛ OTP و ثبت از داخل UI اندروید اجرا نشدند. دریافت کد توسط کاربر و تأیید موفق آن، تحویل واقعی پیامک این نوبت را تأیید کرد. شواهد عمومی بدون شماره، کد ورود، توکن نشست یا کد پیگیری در [stage-otp-account.json](evidence/stage-otp-account.json) و [stage-request-create.json](evidence/stage-request-create.json) ذخیره می‌شوند.

بازارسال همان payload با همان submission_token نیز HTTP 200 داد: همان request_id و همان کد پیگیری، duplicate=true و دقیقاً یک ردیف در حساب؛ رکورد دوم ساخته نشد. این آزمون تکرار کنترل‌شده است، نه شبیه‌سازی قطع شبکه.

## آزمایش‌نشده و کار باقی‌مانده

آزمون کامل OTP تا رسید از داخل APK، بازیابی پس از قطع واقعی شبکه، جداسازی حساب‌ها، انقضای نشست و دستگاه فیزیکی هنوز انجام نشده‌اند. نتیجه API را معادل تست UI اندروید نمی‌دانیم.

افزودن تصویر در UI پیاده نشده است. مرکز گارانتی در مسیر واقعی Stage در مرورگر باز می‌شود و جریان Native آن تکمیل نیست. پرداخت، فایل خصوصی و پشتیبانی آزمایش نشده‌اند. بنابراین APK همچنان آزمایشی است و نسخه نهایی تأییدشده محسوب نمی‌شود.

بررسی خودکار قبلاً POST شامل OTP را به علت نبود شماره آزمایشی مجاز رد کرده بود. پس از ارائه شماره و کد از سوی کاربر، ارسال و تأیید واقعی با موفقیت اجرا شدند؛ مانع آن مرحله رفع شده است.

هیچ تغییری در namyranservice.ir یا namyran.ir انجام نشده است. ادغام و انتشار Production انجام نشده‌اند.
