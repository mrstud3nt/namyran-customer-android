# ورود مشتری نسخهٔ ۰.۵.۰ Stage

## طراحی و اجرا

چهار تصویر ZIP ارسالی با فرم‌های Native در Compose جایگزین شدند. ورودی شماره، انتخاب روش ورود، نام کاربری و رمز با نمایش/پنهان‌سازی، OTP با کادرهای مجزا و یک ورودی قابل Paste، ارسال مجدد، انقضا، خطای شماره و کد، ثبت‌نام پیامکی و بازیابی دسترسی پیامکی پیاده شده‌اند. تزئین بالای صفحه یک فایل مستقل شامل وسایل خانگی است. هیچ تصویر فرم یا اسکرین‌شات به‌عنوان رابط برنامه استفاده نمی‌شود. لوگوی موجود پروژه نگه داشته شده است.

مرجع ۰۲ برای فرم تیره با حاشیهٔ آبی و دکمهٔ طلایی مبنا قرار گرفت. مرجع ۰۴ نسخهٔ روشن متفاوتی دارد. فرم رمز فعلی با همان ساختار در پوستهٔ تیرهٔ یکپارچه اجرا شده است. جزئیات تصویری طبیعیِ تجهیزات از یک تصویر تزئینی مستقل در هدر تأمین می‌شود.

## قرارداد واقعی

- منبع Android آخرین commit شاخهٔ PR۳ یعنی 9424d62 است.
- Stage فهرست REST مسیرهای POST برای otp/send، otp/verify، otp/session و otp/logout را منتشر می‌کند. مقصد همهٔ درخواست‌ها Stage است.
- Core در منبع موجود کد چهاررقمی تولید و اعتبارسنجی می‌کند. تصویر مرجع OTP شش جایگاه دارد. UI چهار جایگاه مطابق قرارداد سرور نمایش می‌دهد.
- زمان انقضای OTP و انتظار ارسال مجدد از expires_in و resend_in خوانده می‌شوند. remaining_seconds در خطای cooldown رعایت می‌شود.
- نشست در Android Keystore محافظت می‌شود. ورود سرد پس از اثبات نشست باز می‌شود و بارگیری درخواست‌ها دیگر مانع نمایش حساب نیست. بازگشت سریع به برنامه تا ۶۰ ثانیه بررسی تکراری نشست را آغاز نمی‌کند.
- Google در Core از AJAXهای nsc_google_challenge و nsc_google_login استفاده می‌کند. برنامه nonce و client_id را از همان چالش می‌گیرد، از Credential Manager توکن Google دریافت می‌کند و آن را برای اعتبارسنجی سمت Core می‌فرستد. اگر شماره هنوز پیوند نخورده باشد، مرحلهٔ OTP لازم می‌ماند. نشست Google فقط پس از پاسخ معتبر Core پذیرفته می‌شود. آزمون چالش زنده Stage پاسخ ۴۰۳ داد، بنابراین موفقیت ورود Google تأیید نشده است.

## کارهای لازم Core و حساب Google

مسیر ورود با نام کاربری/رمز مشتری، ایجاد رمز و بازنشانی رمز در قرارداد عمومی فعلی شناسایی نشد. فرم رمز وضعیت در دسترس نبودن این روش را نشان می‌دهد و راه ورود پیامکی ارائه می‌کند. ثبت‌نام و بازیابی دسترسی موجود از تأیید شمارهٔ مشتری استفاده می‌کنند و ادعای ایجاد رمز یا تغییر رمز ندارند.

برای تکمیل رمز لازم است تیم Core مسیرها، قواعد حساب مشتری، اثبات مالکیت OTP، یک‌بارمصرف بودن توکن بازیابی، سیاست رمز، محدودسازی تلاش‌ها و ابطال نشست‌ها پس از تغییر رمز را عرضه کند. از endpointهای تکنسین یا حساب مدیریتی وردپرس برای مشتری استفاده نشده است.

برای Google باید ورود Google روی Stage فعال شود و OAuth Android برای package آزمایشی و SHA امضای APK تنظیم شود. SHA گواهی debug در هر runner تازه ممکن است متفاوت باشد، بنابراین برای آزمون پایدار Google باید کلید امضای Stage ثابت با دسترسی مجاز تهیه شود. کلید خصوصی در مخزن قرار نمی‌گیرد. Client ID از سرور می‌آید و Client Secret وارد برنامه نمی‌شود.

## آزمایش‌ها و محدودیت‌ها

تست خودکار شبیه‌ساز بدون ارسال پیامک، درگاه ورود، فرم رمز، بازیابی پیامکی، ثبت‌نام، خطای شماره، خطای OTP، ورود نمایشی ایزوله، چرخش و بازکردن دوبارهٔ برنامه را بررسی می‌کند. موفقیت Build و این تست‌ها به‌معنای تأیید دریافت SMS یا ورود واقعی Google نیست. بررسی واقعی OTP نیازمند کد دریافتی حساب مجاز Stage است.

تشخیص شهر از چند تأمین‌کنندهٔ موقعیت و آخرین موقعیت تازه استفاده می‌کند، نام شهر را از فیلدهای مختلف Geocoder در زبان فارسی و انگلیسی تطبیق می‌دهد و شهر مبهم را بدون تأیید کاربر انتخاب نمی‌کند. روی دستگاه فاقد Geocoder یا سرویس موقعیت فعال، انتخاب دستی همچنان لازم است. تست واقعی تشخیص شهر روی دستگاه کاربر انجام نشده است.
